pr-reviewer 架构说明

面向 GitHub PR 的 LLM 代码审查 Agent。本文说明代码结构、数据流、每层的职责，以及若干看起来可以简化、但实际上是为了修复具体故障而存在的设计。

语言 Python 3.11+ 代码 66 个模块 / 9,461 行 Prompt 22 个文件 / 1,154 行 测试 133 条离线断言 模型 可替换（默认 deepseek-v4-pro）

1. 系统由三条独立的链路组成

它们共享同一套审查流水线，但触发方式、时间尺度和失败模式完全不同，所以是三个独立进程。

  ① 事件链路（秒级响应，分钟级执行）
     GitHub ──webhook──> nginx(TLS) ──> serve ──入队──> 队列(磁盘) ──> worker ──> 发帖
                                          └─ 202 立即返回              ↑
  ② 对账链路（20 分钟一轮）                                            │
     systemd timer ──> scan ──────────捡回 webhook 丢投的────────────────┘

  ③ 评测链路（离线，不触碰生产）
     语料(corpus.json) ──> benchmark-run ──> LLM judge ──> scorecard
链路入口回答什么失败时
事件serve + workerPR 有新修订，审它丢投 → 由对账链路兜底
对账scan有没有漏掉的修订下一轮重来，幂等无副作用
评测benchmark-run这次改动比上次好还是差按 PR 检查点，重跑只补缺失

为什么必须是三个进程：GitHub webhook 10 秒超时，而一次审查要几分钟。接收端只做验签、入队、返回，任何多余的工作都会把"审查慢"变成"投递失败"。

2. 审查流水线

三条链路最终都调用同一条流水线。它是一个逐文件的管道，每一级只做减法——除了第一级，后面每一级都只能删除或降级发现，不能新增。

  PR diff
    │
    ├─ 1. 解析 + 行号栏渲染          diffing/parser.py
    │      旧行号 | 新行号 标记内容 ← 引用校验的唯一依据
    │
    ├─ 2. 按 glob 路由规则包          policy.py + resources/policies/
    │      general.md + {python,typescript,java,go}.md
    │
    ├─ 3. 审查（可带工具、可 N 路）    pipeline/review.py
    │      单次调用 或 agentic 探索 或 N 路 + 多数决聚合
    │
    ├─ 4. scope 校验                  diffing/scope.py
    │      引用必须落在行号栏里，且至少一条命中本次新增行
    │
    ├─ 5. 资格闸门（便宜）             pipeline/qualify.py
    │      启发式正则 → discard / pass / validate
    │      info 走可执行性判据，不进昂贵的验证器
    │
    ├─ 6. 深度验证（昂贵，agentic）    pipeline/validate.py
    │      带只读工具调查 → TP / FP / FP_OOS / TP_SI / IND
    │
    ├─ 7. 应用裁决 + 重写摘要          pipeline/apply.py, render.py
    │
    └─ 8. 渲染 + 发帖                  pipeline/inline.py, sources/github.py

成本分布是刻意的：实测一轮中 26 条发现在第 5 级（一次文本调用）被拦下，只有 7 条进入第 6 级（多轮 agentic 调查）。把过滤放在便宜的一端，是这条流水线能负担深度验证的前提。

4. Prompt 是数据，不是代码

1,154 行 prompt 全部在 resources/ 下，按角色 / 任务 / 规则三类组织。改判据不需要动 Python。

结构

resources/
├── role/default/     角色定型，各 1–3 行
├── tasks/            10 个任务模板
├── rules/
│   ├── general.md          通用准则与指令
│   └── language_rules/     4 个语言包
└── policies/default.json   glob → 规则包路由

两条硬约定

  • 角色里不写"不要做 X"——否定式会让被否定的概念更突出
  • 规则文件标题层级 ≥ H3——它们被拼接进 H2 之下，更高层级会破坏锚点语义
  • 模板不用 str.format——prompt 里嵌了大量 JSON 和代码示例，花括号会让它崩溃

5. 换模型是一个 flag

每种端点用什么方式约束输出、有多大上下文、认哪些厂商字段，写在 provider/profiles.py 里。流水线本身不含任何厂商分支。

被忽略的约束和被执行的约束长得一模一样，直到你去检查。 一个拒绝未知字段的服务器会响亮失败、一分钟就修好；一个接受 strict: true 却不执行的服务器，会返回流畅的、自己发明的 schema。所以无论端点承诺什么，返回值一律解析并校验。

6. 六处不能简化的设计

下面每一条都对应一次真实故障。它们看起来都可以更简单。

去重按修订号，不按时间戳

原判据是"最新报告时间 > PR 最后更新时间"。在"每次推送都审"的场景下会稳定漏审：推 A → 开始审 A → 推 B → A 的报告发出（时间晚于 B 的推送）→ 下一轮判定已审 → B 永远不会被审。现在每份报告把它回答的 commit 写进标记，判据是"这个 commit 有没有报告"。这也是重试安全的前提——没有它，每个重试机制都会变成重复发帖的来源。

解码侧五层防御

去围栏 → 大括号提取 → 重驱动模型 → clamp 截断超长字段 → 校验。写这套时以为是兜底，实际每一层都被真实触发过。

Schema 完全内联

Pydantic 生成的 $defs 间接引用不被识别时，嵌套定义压根进不了语法约束，strict 静默降级成"提示"，模型返回自己发明的字段名。所有 $ref 现在递归展开成自包含文档。

验证器无工具调用的裁决降级为 INDETERMINATE

没读过代码就下的结论是意见，不是发现。

每个任务 pin 到自己的 commit

worker 消费的连续两个任务往往是不同 PR、甚至不同仓库。读文件的阶段若指向一份固定检出，验证器不会报错——它会对毫不相干的代码给出自信的裁决。没有配置检出的仓库，这些阶段被关闭而不是指向进程的当前目录。

计费失败是 FATAL，不是容量限制

"余额不足"曾被归类为容量类，于是每次调用重试 10 次 × 30 秒退避——反复撞一堵永远不会消失的墙。等待能解决限流，对空钱包毫无作用。

7. 评测

没有这套，改 prompt 就只能靠感觉。它回答的是"这次改动比上次好还是差"，不是"这个 agent 好不好用"。

  语料      corpus.json — 每条 = 一个根因、一个位置、一个 commit 能修完
  跑分      benchmark-run --corpus X --run-dir Y [--agentic] [--checkout-repo Z]
  检查点    每个 PR 单独落盘，中断重跑只补缺失
  打分      precision 数 finding，recall 数缺陷（两种单位分开计）
  分桶      按 severity / 按是否需要跨文件 / 按价值分级
配置precisionrecallF1
裸审查器0.1390.4380.211
+ 验证流水线0.1640.4380.238
+ 收紧规则包0.2090.4380.283

这个数字不能读作"准确率"。 语料只有 16 条、单一语言、由本项目作者标注。一条匹配不上的发现，可能是它错了，也可能是它对了但没被标注——两者在数据上分不开。这套 harness 是相对刻度，不是绝对评价。
